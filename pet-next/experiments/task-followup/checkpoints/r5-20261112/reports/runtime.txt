Scope distinction
The natural continuation story is an actual user-facing application path with filesystem restoration by an external producer. The future/offline-due cases deliberately schedule a controlled public-API job, proving the durable scheduler boundary; they are not presented as naturally generated production user stories. Their jobs re-evaluate current state and create no tools or reminders because those tasks have no result yet.
The script uses explicit demo settings minGapMs=1500, intervalMs=150, wakeAfterMs=1500, reminderQuota=100, quiet hours disabled and timezone UTC; this is not a performance/policy-quality test. All child argv are recorded and none contains --clock, tick, wake or a manual clock advance. Service metadata records clock=real. Each service is bounded and exited before a writer CLI command resumes. Read-only SQLite inspection runs concurrently; no competing database writers or external endpoints are used.

Confirmed remaining issue: one min-gap waiting question becomes six persisted jobs and six useless re-evaluations.
Evidence: real-final/natural-continuation/after-service.json and state/service.log.
For one (ticket_id, reason=quiet, decision_id), six distinct job IDs have dueAt:
10:10:06.844, 06.995, 07.147, 07.299, 07.450, 07.602 UTC.
All six end done with attempts=1. Each wake log has proposals=0 and notifications=0. The one actual question has only one notification. The extra work is redundant scheduler wake/re-evaluation, not repeated user reminders or duplicate tool execution.
Root in code:
- runtime/engine.ts:905-919 computes a fresh dueAt=now+minGap on every sync for the same undelivered open attention.
- runtime/scheduler.ts:31-34 includes dueAt in stable job ID; schedule (40-65) always saves a new row for a changed dueAt.
- runtime/db.ts:789-815 only upserts by job_id and never coalesces the logical (ticket,reason,decision) wait.
- service/scheduler-service.ts:127-128 calls reevaluate before handleDue each loop, so the same pending question is repeatedly scheduled before its delivery becomes legal.
This contradicts scheduler.ts's documented one-logical-wait contract. The existing demo's 'no busy loop' check only compares dueAt against now-60 seconds; it does not test logical job cardinality or useless wake count. We did not extrapolate the observed 150ms redundant wakes into a claim of unbounded CPU use or measured long-run failure.

Service/feature boundary
serve --scheduler explicitly selects RealClock and is independent of HTTP/browser UI. Default serve still starts only the HTTP panel; it does not enable this experimental scheduler. The service calls recover at startup, then reevaluate and wakeDue in a bounded timer loop. The current user-facing automatic continuation can arise from reevaluate; the independent due controls separately prove actual durable-job claiming, rather than treating any polling-driven reminder as proof of a scheduled wake.

Not proved
No 12-hour/all-day stability, crash between claim and finish, power-loss/multiwriter/cross-machine guarantee, real-model reasoning, remote task execution, or live user-interruption benefit. Windows/browser outcomes are owned by the parent review. This real-time script does not validate the FakeClock R5 eval or its scoring; those are a separate review.
